ML Intern Assignment  
Insurance Enrollment Prediction + Outreach Assistant Agent 
Objective 
Build an end-to-end machine learning system that: 
1. Predicts whether an employee will opt in to a new voluntary insurance product, using a multi-file, 
deliberately imperfect HR/benefits dataset that is not the plain "predict insurance enrollment" tutorial 
dataset, and 
2. Exposes that model through a small tool-using Outreach Assistant agent that ranks employees for a 
benefits team with a limited outreach budget, and can explain individual predictions without leaning on 
protected attributes. 
The assignment is designed to assess: 
• 
Your ability to investigate multi-table HR data, join tables correctly, and engineer features under real 
messiness (mixed date formats, sentinel codes, inconsistent categorical labels, conflicting duplicate 
records). 
• 
Your judgment about which fields are legitimate predictors versus target leakage, and which fields are 
legitimate predictors but ethically/legally risky to act on in an insurance context. 
• 
Your ability to wrap a model in a simple agentic interface (tools + ranking + refusal rules), not just a 
notebook metric. 
Python is expected. A normal laptop is enough, no GPU required. 
Attachments: the two CSV files described under Data are attached to the email that sent you this document. 
We are not sharing any starter code or repository, you build the full solution from scratch. 
Core Functional Requirements 
1. Multi-Table Data Investigation & Cleaning 
You receive two files (see Data). You must join them thoughtfully. 
At minimum: 
• 
Profile both tables: missingness, dtypes, cardinality, duplicates, impossible values. 
• 
Resolve or explicitly policy-handle duplicate employee_id rows with conflicting enrolled labels pick a 
policy (drop both, keep most recent contact, majority vote across the pair, etc.) and state it. 
• 
Parse the messy operational fields: application_date (mixed formats / blank), last_contact_date (some 
rows show contact happening after the application, flag or fix, don't silently feed it to a model), 
inconsistent casing in last_contact_channel (Email / EMAIL / e-mail / ...), and free-text 
plan_tier_requested (Premium / premium plan / PREMIUM / Gold Plan / ...). 
• 
Handle the prior_year_enrolled sentinel: 1 means "no prior-year record (new hire)", not "not enrolled." 
Treating it as a literal 0/1 numeric feature without addressing the sentinel is a real bug, not a stylistic 
nitpick. 
• 
Document every non-trivial cleaning decision.

2. Feature Engineering  
• 
Engineer features from the messy dates, contact-channel, and plan-tier text. 
• 
Join the region table and reason about which region-level columns would realistically be available at the 
moment you'd need to make a prediction. 
• 
Classify every feature as usable, analysis-only, or forbidden / leaky, and justify the split. 
• 
At least one field nearly reconstructs the target outright treat any suspiciously strong predictor with scrutiny, 
not blind trust. 
• 
Fairness / compliance checkpoint (required): some demographic fields are present and mildly predictive. 
Using them to prioritize who gets proactive outreach can create disparate treatment even unintentionally. 
State whether your final model uses them and why; if it does, report a subgroup performance breakdown 
and comment on whether any group looks disadvantaged. There's no single correct answer we grade the 
reasoning, not the choice. 
 
3. Model Training & Honest Evaluation 
• 
Train a classifier for enrolled. 
• 
Proper train/test split (or cross-validation), this is cross-sectional data, not a time series, so a plain 
stratified split is fine, but say so. 
• 
Report AUC-ROC and a business-relevant ranking metric (e.g. Precision@K or Lift@K, see the outreach 
framing in §4). 
• 
Beat at least one naive baseline (majority class, or a simple rule like "predict 1 if has_dependents == 
Yes"). 
• 
Report a second evaluation with the leaky column removed if you experimented with it, graders will 
check. 
4. Agentic Layer, Outreach Assistant (Required) 
The benefits team cannot personally contact all 10,000 employees every enrollment window, each region 
has a fixed hr_outreach_capacity in the region table. Build a small tool-using agent (LLM optional) that helps 
the benefits team decide who to contact and can explain why, without hard-coding answers.

•

table, sentinels, leak column, agent, fairness checkpoint) will not pass.
